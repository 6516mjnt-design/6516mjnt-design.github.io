Loop Engineering

2026年8月1日更新

1. エグゼクティブ・サマリー

人間がAIプロンプトを叩くのをやめ、「AIが目標達成まで自律して試行・評価・修正を繰り返す仕組み（Loop）」を設計・構築する手法。

  • 本質的なパラダイムシフト：
    「上手なプロンプトを書く人（Prompt Engineer）」から「自動で回る工場を構築する人（Loop Engineer）」へ、IT人材の価値とレバレッジの支点が移動している。
  • 成功の絶対条件：
    「検証可能性（証拠）」と「停止条件」。検証できないタスクをLoopに載せると、高速でエラーや粗悪な成果物を量産する装置と化す。
  • 最大の倫理的リスク：
    システムが勝手に回ることで生じる「理解の負債（コードのブラックボックス化）」や「認知的降伏（思考停止）」に注意が必要。

2. 背景：AIパラダイムの4世代変遷

AIの活用手法は下図のように進化してきたが、重要なのは「前の世代が消えるのではなく、最新世代の“パーツ”として内包される」という点。

世代 AIパラダイム 人間の役割 主な技術・概念
第1世代 Prompting 手動でプロンプトを入力し指示する プロンプトテクニック
第2世代 Context 適切な背景情報やファイルを提示する RAG、コンテキスト拡張
第3世代 Harness 単一エージェントを安全に動かすガードレールを作る ガードレール、安全装置
第4世代 Loop エージェントを自動的に回すシステム（工場）を設計する ループエンジニアリング
Harnessは「1台の機械を安全に動かす安全装置」、Loopは「工場全体を自動で稼働させる生産管理システム」。

3. Loopを構成する 6つのコアモジュール

Addy Osmani氏の定義に基づく、Loopに必要な6つの構成要素。

 　[ 1. Automations (起動) ] ── (トリガー)
               ▼
  　Loop 内部空間
   　[ 2. Worktrees (環境分離) ]  [ 3. Skills    (知識チップ) ]   [ 4. Sub-agents(相互牽制) ]                 
   　[ 5. Connectors(外部操作) ] 　[ 6. Memory    (外部状態記録) ] ──最重要!
  • 1. Automations（ハートビート / 起動装置）： CI失敗やIssue作成などをトリガーに、人間を介さず自律起動する。
  • 2. Worktrees（防護壁 / 秘密分離）： ブランチ分離などにより、複数エージェント並列稼働時の競合・事故を防ぐ。
  • 3. Skills（知識チップ / 共有知）： プロジェクト固有の構築手順や「過去踏んだ罠」などを記述したルールファイル（例: .claude/skills/build.md）。
  • 4. Sub-agents（相互牽制メカニズム）： 「実装担当」と「粗探し・レビュー担当」を分け、成果物のクオリティを客観的に評価する。
  • 5. Connectors（腕 / 外部連携）： MCP（Model Context Protocol）等を介し、GitHub/Linear/Slack等へ直接アクション（PR作成、チケット更新、通知）を起こす。
  • 6. Memory（状態保持 / 永続化）※最重要： Markdownやタスクボードによる外部状態の保持。モデルは忘れてもリポジトリは忘れないため、再起動時のゼロリセットを防ぐ。

4. 実践：検証可能なループの 5ステップ方法論

Loopを「便利な乱数発生機」にしないための実践ステップ。

  1. Step 1: 目標契約 (完了基準の定義)
    定量化された受け入れ基準（例：エラー率 < 0.1%、P95レスポンス < 1.5s）を設定する。数値化できないものは原則Loopに載せない。
  2. Step 2: Agent実行 (計画・ツール呼び出し・実行)
    タスクを分解し、並列インスタンスや適切なツール（エディタ、ターミナル、検索等）を活用して進める。
  3. Step 3: 証拠フィードバック (ログ・テスト・スクショ)
    AIの「できました」は一切信用せず、テスト結果・実行ログ・スクリーンショット・CIステータスなどの客観的証拠を提出させる。
  4. Step 4: 停止条件判定 (デリバリー / ロールバック / 移送)
    以下の4パターンで終了処理を行う。
    • 合格： 基準クリア ➔ 自動デリバリー
    • ロールバック： リスク検知・目標離脱 ➔ 変更取り消し
    • 人間に引き渡し： 判定不能・重大判断 ➔ エスカレーション
    • タイムアウト： ラウンド上限超え ➔ 中断してレポート出力
  5. Step 5: 経験の還元 (Skills・ルール更新)
    成功・失敗パターンを Skills やルールにフィードバックし、次回の精度とスピードを向上させる。

5. チーム導入：6つのステップとゴー/ノーゴー判定

導入の 6ステップ

  1. タスク選定： 小さく定量化できるもの（CI赤信号の修復、ログ点検、テスト補完等）から開始。
  2. 目標契約の記述： 入力・出力・定量合格基準・禁止事項を定義。
  3. ツール接続： リポジトリ、テスト環境、MCP、Issueトラッカーに接続。
  4. センサー追加 ＆ 【品質ゲート #1】： 証拠（ログ・スクショ等）が揃わなければ次に進ませない。
  5. 停止条件設定 ＆ 【品質ゲート #2】： タイムアウトや人間への引き渡しラインを厳格化。
  6. 経験の蓄積： ルールやevalケースを更新し、組織知化する。

6. 潜む 3つの危険な罠（注意点）

ループエンジニアリングがスムーズに回れば回るほど、人間側のリスクが高まる。

① 検証の死角（Blind Spot of Verification）

「完了（Done）」はAIの自己申告になりがち。証拠（Evidence）を強制出力させないLoopは、ただの「自信過剰な乱数発生機」になる。

② 理解の負債（Comprehension Debt）

人間がコードを書かないため、システム全体の構造理解から離脱していく。後で障害対応をする際、誰が書いたかわからないコードの山と向き合うことになる。

③ 認知的降伏（Cognitive Surrender）

「AIがそう言っているから」と自身の批判的思考を放棄し、提案を呑んでしまう現象。定期的に自身のレビュー基準を言語化して解毒する必要がある。

7. まとめ

ループエンジニアリングの難しさは「1つの答えを出すこと」ではなく、「正解を出し続ける機械（メカニズム）を作ること」にある。今後のエンジニアの差別化は、仕事をAIに丸投げすることではなく、業務の本質を深く理解したうえで「堅牢で検証可能なLoop」を組み上げられるかに依存する。
