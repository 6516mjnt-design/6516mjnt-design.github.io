PHP 2 Shell

PHP 2 Shell と呼ばれるセキュリティ上の欠陥とその対策

作成日：2026年11月10日
2026年10月、ウェブサイトを動かす基礎プログラム「PHP」に、外部からサーバーを乗っ取られるおそれのある欠陥「PHP 2 Shell」が見つかった。 確認されたのは「危険があるかもしれない」という段階で、悪用された事例は確認されていない。

はじめに

国内では、念のためサービスを一時停止した組織があったとされている。ただし、欠陥が悪用されて情報が盗まれたと確認された事例ではない。 多くの組織が「止める」以外の判断材料を持てなかったと見られることが、この件の大きな教訓である。

この報告書の結論は次の三つです。

  • 今すぐやるべきこと：使っている PHP のバージョンを確認し、修正版に更新すること。古いバージョンを使い続けている場合は、新しいバージョンへの移行を急ぐ必要がある。
  • 中長期でやるべきこと：「どこで何が動いているか」を常に把握できる体制を作り、問題が見つかったときに素早く直せる仕組みを整えること。
  • 根本的な作り方の見直し：より安全な言語の利用、システムの隔離など。時間がかかるため、段階的に進めること。

1. 基本の理解：この欠陥は何か

1.1 ウェブサイトの「受付」と「作業場」

ウェブサイトの仕組みは、郵便局に例えると分かりやすいかもしれない。

  • 受付（サーバーの基盤部分）：外からの荷物（リクエスト）を受け取り、中身を読み取って振り分ける。
  • 作業場（PHP で書かれたプログラム）：振り分けられた荷物に対して、ページの作成などの実際の仕事をする。

今回の欠陥は、このうち受付にあたる部分、つまり PHP という言語の内部の処理にある。受付で荷物を読み取る段階で、仕組みの隙を突かれるおそれがある。 そのため、作業場のプログラムをどれだけ丁寧に書いても、受付の隙は防げない。

1.2 「解放後使用」とは

コンピュータは、作業のために一時的にメモリ（作業用の机の広さのようなもの）を借りる。仕事が終わると、その机を返す。

今回の欠陥は、この「返したはずの机」を、まだ使っているかのように扱ってしまうことで起きるおそれがある。 返したはずの机に悪意のある人が自分の書類を置いておくと、プログラムはそれを正しい指示として読んでしまい、サーバーを操られるおそれがある。

これは仕組みを分かりやすくするための比喩。専門用語では「解放後使用（UAF）」と呼ばれる種類の問題で、公式の発表では正確な種類はまだ明記されていない。

1.3 どれくらい深刻か

国の機関であるIPA（情報処理推進機構）の注意喚起では、インターネット越しに、ログインなしで、サーバーに好きなプログラムを動かされるおそれがある。 深刻度を示す点数（CVSS v4）は 9.2 で、10点満点に近い高い数字である。

ただし、「攻撃が成功した」と確認されたわけではない。現時点では「攻撃されるおそれがある」段階の注意喚起。

2. 何を、どう直せばよいか

2.1 修正版のバージョン

次のバージョンより古い PHP は、この欠陥の影響を受けるおそれがある。

使っている PHP の系統直すべきバージョン（以上）
8.2 系8.2.35
8.3 系8.3.36
8.4 系8.4.27
8.5 系8.5.12
8.1 以前修正版はありません（サポート終了）

「8.1 以前」は、直す版がもう提供されないため、新しいバージョンへの移行が必要。

なお、解説記事では PHP 5 以降の版が影響を受ける可能性があると報じられている。古い版は、すべて対象に含まれるものとして扱うのが安全。

2.2 「バージョン」とは何か

PHP のバージョンは、ソフトウェアの世代番号。例えば「8.2.35」は、8.2 という世代の 35 回目の修正版、という意味です。 数字が大きいほど新しく、後ろの番号が大きいほど多くの修正が入っている。

自分のサーバーで使われている PHP のバージョンは、サーバーの管理者や、制作を依頼した業者に確認するのが確実である。

2.3 更新できないときは

すぐに更新できない場合には、次のような一時的な対策がある。

  • アクセスを制限する：外部から使える人や場所を絞ります。
  • WAF を前に置く：WAF とは、ウェブの防犯カメラや検問所のような仕組みです。怪しい荷物を途中で止める。 ただし、根本的な修正の代わりにはならず、時間を稼ぐための手段である。
  • 一時的に止める：危険性が残ったまま動かし続けるのを避けるための、最後の手段です。止めればサービスは利用できなくなる。

3. なぜ多くの組織が「止める」ことになったのか

3.1 止める以外に判断できなかった

今回、組織が止める判断をした理由として、次の点が考えられる。

  • 自分のサーバーで、どの PHP が動いているか把握できていなかった。
  • 欠陥の影響を受けるかどうかを、すぐに判断できなかった。
  • 直す手順を、すぐに用意できなかった。

判断材料がないため、「念のため全部止める」しか選べなかったと見られる。 これは、家の鍵が壊れたかもしれないのに、どの扉が壊れているか分からず、家中の扉を閉め切って出かけられなくなる状態に似ている。

3.2 止めることにもコストがある

サービスを止めれば、利用者や業務に大きな影響が出る。一方、危険なまま動かし続ければ、乗っ取りのリスクを抱えたままになる。 どちらにもコストがあるため、大切なのは止めるかどうかを、事前に決めた基準で判断できることである。

3.3 「無料だから使い続けた」は一部だけ正しい

PHP や Linux は無償で使えるため、「費用をかけずに導入できる」というのは事実である。しかし、無料なのはソフトウェアの利用料だけ。 更新作業、セキュリティの監視、担当者の育成などには費用がかかる。問題は、「無料＝安い」と受け取られ、こうした費用が見えないままになっていたことにあると考えられる。

4. 欠陥の作り方を見直す必要性

4.1 「安全な言語」とは

プログラムを書く言語には、メモリの扱い方の違いがある。

  • 手動で管理する言語（C 言語など）：速くて自由度が高い一方、使い終わった机を返し忘れたり、返した後も使ったりするミスが起きやすくなる。
  • 安全な仕組みを持つ言語（Rust、Go など）：こうしたミスを、言語の仕組みで大きく減らせる。

ただし、安全な言語に変えても、すべての問題がなくなるわけではない。「ミスの種類を減らす」効果があるということ。

4.2 「隔離」とは

もう一つの考え方は、仮に一か所が乗っ取られても、被害が広がらないように区切っておくことである。

  • コンテナや仮想マシン：一つのサーバーの中を、独立した小部屋に分けるようなものです。
  • 最小限の権限：各プログラムに、必要最低限の操作だけを許可します。

これらは、一般の組織でも取り入れやすい方法である。

4.3 OS の作り替えについて

OS（パソコンやサーバーの基本ソフト）を、まったく新しい設計のものに置き換える、という考え方もある。理屈としては安全性を高めますが、多くの組織にとって現実的な選択肢ではない。 まずは、隔離や権限管理といった身近な方法から進めるのが現実的である。

5. 歴史の補足

今回の件は、古い技術を使い続けてきたことにも関係する。

技術誕生

6. 今後の取り組み：段階的なロードマップ

  • フェーズ 0：今すぐ（〜1 か月）
    • 外部に公開しているサーバーから優先して、使っている PHP のバージョンを確認する。
    • PHP 8.1 以前を使っている場合は、移行の計画を立てる。
    • 修正版（8.2.35 / 8.3.36 / 8.4.27 / 8.5.12 以降）へ更新する。
    • すぐに更新できないものは、アクセス制限や一時停止の基準を決めて対応する。
    • WAF を前に置き、ルールを最新の状態にする。
    • IPA や JPCERT/CC などの注意喚起を、定期的に確認する。
  • フェーズ 1：短期（0〜6 か月）
    • どのサーバーで何が動いているかを、常に一覧で把握できるようにする。
    • テストを含めた自動更新の仕組みを作る。
    • 緊急時に止めるかどうかを判断する手順書を作り、練習しておく。
    • 古くなったソフトウェアを使わなくするための計画を立て、予算を確保する。
  • フェーズ 2：中期（6 か月〜2 年）
    • 新しく作るシステムでは、安全な言語の採用を基本方針にする。
    • 危険性の高い古い部分から、順番に作り替える。
    • 隔離や権限管理を、標準的なシステムの作り方にする。
  • フェーズ 3：長期（2〜5 年）
    • システムを発注するときの条件に、「安全性」「更新期限」「ソフトウェアの部品表（どの部品を使っているか）の提出」を加える。
    • 多くの業者を経由する契約の形を見直し、セキュリティに必要な費用を正しく見積もる。
    • セキュリティを担当する人材を育て、定期的に攻撃を想定した訓練をする。

7. 今すぐできるチェックリスト

  • 使っている PHP のバージョンを確認する（外部公開のサーバーから優先）
  • PHP 8.1 以前を使っていないか確認し、使っていれば移行を計画する
  • 修正版（8.2.35 / 8.3.36 / 8.4.27 / 8.5.12 以降）へ更新する
  • すぐに更新できない場合の対策（アクセス制限・一時停止の基準）を決めておく
  • WAF を前に置き、ルールを最新にする
  • IPA や JPCERT/CC の注意喚起を定期的に確認する担当者を決める

9. 確認できていないことと注意点

  • 組織が受けた実際の被害（情報流出や停止件数）は、今回の確認では把握できていない。
  • 欠陥の技術的な詳しい仕組みは、今後の公式発表で変わる可能性がある。正確な情報は、PHP の公式発表や IPA の注意喚起で確認すること。
  • 「止めた組織の数」などの数字は、出典が確認できていないため引用していない。
